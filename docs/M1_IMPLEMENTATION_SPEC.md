## 2. 已确证的规则冲突（不得静默自行创造数值）

任务第 3—4 节给出的 M1 数值要求，与仓库现有 v0.7 已冻结数据存在**直接冲突**。任务禁止我擅自重新设计经济与数值，也禁止凭空补造，故此处只登记冲突，不作裁决。

### 冲突 A：开局货币量级

| 项 | 来源 | 值 |
| --- | --- | --- |
| M1 任务第 4 节 | 任务书 | 开局 **8 金币**；一转购买价 **4**，出售返还 **2** |
| v0.7 实测 | `data/xuantong_live.json` → `start_kits[].yuan_stones` | **95 / 100 / 85 / 105 / 90 / 100 / 100 / 105** 元石 |

`docs/CORE_ECONOMY_E1.md` 第 13 行已明确裁决并预警：

> 八道现有开局85–105元石、二转炼制费18元石均未审定，**禁止交Codex任意沿用**。

同时 E1 记录原著市价：普通一转蛊约 **250 元石**（第二卷第63节），普通一转 ≤500 元石（第二卷第79节）。M1 的"4 金币买一转蛊"与已核证原著价格相差约 **60 倍**，也与 v0.7 现存 85—105 元石不一致。

**需裁决**：8/4/2 是"独立于元石的 M1 专用小货币"，还是"元石的重新定标"？若是后者，与已核证原著价格及 `CORE_ECONOMY_E1.md` 的禁止性裁决冲突。

### 冲突 B：24 只一转蛊的实际能力粒度

任务第 3 节要求"24 只一转蛊的**全部有效技能**"，并重点测试记痕反击、听息防御、护盾吸收归因、变招信息延迟等具体机制。

现有 v0.7 实测（`data/xuantong_live.json`，24 只一转蛊的 `runtime_kind` 分布）：

| runtime_kind | 数量 | 说明 |
| --- | --- | --- |
| `inspect` | 8 | 全部退化为同一通用动作 |
| `shield` | 8 | 全部退化为同一通用动作 |
| `strike` | 6 | 全部退化为同一通用动作 |
| `recipe_component` | 2 | 无战斗效果 |

`docs/CORE_RULES_MILESTONES.md` 第 38 行已如实记录该局限：

> v0.7 已把 32只原创蛊映成通用 strike/shield/inspect/component，**不能宣称完整继承其各自特殊能力**。

并且存在**语义错误**：执枢道「系令蛊」标注为战斗攻击，`runtime_kind` 却是 `inspect`；观复道「记痕蛊」标注为战斗攻击，`runtime_kind` 同样是 `inspect`。这两个名字正是任务第 3 节点名的"记痕反击"与相关机制来源。

**需裁决**：24 蛊各自的"有效技能"完整定义（冷却、目标、伤害/护盾/状态、触发条件）在 D2.2 数值表中。该表不存在。若由我自行拟定，即属任务禁止的"凭空补造"与"重新设计蛊虫能力"。

### 冲突 C：战斗时钟与既有战斗核

任务第 3 节要求"0.5 秒 tick 的统一确定性时钟"与"P0—P5 固定事件执行顺序"。

现有实现：`js/combat_core.js` 明确声明为**唯一 Web 战斗核**，并要求禁止回退第二套结算：

> 唯一 Web 战斗核（合并：逻辑=MVP，壳=Lab）… 禁止第二套结算。

该核基于 `js/mvp_logic.js`（27.8 KB）与 `js/battle.js`（28.5 KB），是既有的事件/意图/反击模型，**不是** 0.5s tick + P0—P5 模型。

**需裁决**：M1 的 tick/P0—P5 模型是替换唯一战斗核，还是与其并存？若替换，与"禁止第二套结算"的既有约束及 v0.7 全部战斗测试（`tests/lab_combat.test.mjs` 38.8 KB 等）的关系需明确。任务要求"不引入旧规则干扰 M1"，但也要求"保留 v0.7 供兼容"——二者需要边界定义。
