## 2. 视觉要求和明确未通过项
- 固定主要游戏操作画幅，桌面优先 16:9；在 1366×768 下不应靠整页滚动寻找交互入口。商店/蛊仓分状态切换；局部列表可滚动，但要保证可访问且不遮挡核心操作。
- 移动端独立响应式布局，不将桌面宽屏硬压缩；保留固定出战入口。
- 当前东方玄夜、暖金、玉青、烟紫的视觉基调是**候选**，不是绝对禁止调整。用户反感低质、噪点重、过度复杂的 UI，追求清透的电影光影、角色魅力和真正的技能演出。
- 当前玩家角色仍是符印/法相占位，敌方立绘覆盖不一致，蛊虫卡缺统一高品质绘制。只是 CSS 渐变或发光**不能**算商业级美术完成。
- 新视觉应优先考虑角色/敌人立绘、24+蛊虫卡面的统一视觉语法、攻击/护盾/反击/夺蛊清晰反馈，再考虑微交互动效。
- 风格审计至少要有**1280×720、1366×768、1920×1080、390×844** 真实浏览器截图，以及关键游玩状态：道途/商店/满蛊仓/战斗/战利品/结算。
- 不凭 Node/Chromium 通过声称视觉达标；必须人工观看截图并对照参考游戏。

## 3. 两个对话的并行开发规则（强制）
- **新视觉对话只能在独立分支工作**：建议 `feat/m2-visual-pass`，从开始工作的 M2 最新 HEAD 分出，另建独立 Draft PR 指向当时 M2 工作分支；不要直接向 PR #2 的 `feat/m2-extended-run` 推视觉提交。
- **原 M2 对话是玩法 Owner**：可继续修改 `js/m2_game.js`、`data/`、`tests/` 等业务文件。视觉对话尽量只改 `css/m2_art.css`、视觉专属模块/资源和测试截图；涉及 `m2.html` 容器或 `js/m2_game.js` 的 DOM 改造，先以独立 PR 提交，标注触及的 DOM/函数与冲突风险，等待 M2 Owner 在当前开发进度下集成。严禁覆盖另一个对话刚改的文件。
- 可以设计替代页面布局，但不要引入新战斗机制、偷改出战负载上限或修改敌人收益以符合美术方案。
- 修改前审计现有美术资产版权和适配性，生成资产也要记录用途与状态。旧 Library 的候选不等于实装。
- 每轮均：**短审计 → 素材或代码落地 → 浏览器实测 → 截图人工检查 → GitHub PR → Library 记录**。不要只给空泛建议或提示词。
- 视觉验收通过后由原 M2 对话决定合并/集成；不要自行合并至 M1、M2 业务分支或 master。
